When you open a project

You do not need to know a command to get started. When a session starts, the suite checks the folder and offers the right next step. It writes nothing until you say yes.

What it findsWhat Claude does
Configured — .design-suite/profile.json existsNothing. You are set up.
New — no source code yetOffers /onboard-new-client.
Existing — code, but no .design-suite/Offers /run-chain understand-existing-project, the guided setup below.
Half set up — .design-suite/ but no profileSays most skills will refuse; suggests doctor.py or resuming the guided setup.
Can't tell — home folder, unreadable, or too big to check quicklySays so and suggests nothing. Asks you if you bring it up.
Turning the offer off. For one project, add an empty .design-suite-onboarding-declined file at the project root (Claude creates it only if you ask). For your whole machine, set DESIGN_SUITE_NO_ONBOARDING=1.

Before setup: the "not configured" notice

In a project that isn't set up, the on-edit hooks say so once per session — "nothing is checked on edit (this is not a clean result)" — so silence is never mistaken for a pass.

Exit 2 means "could not check". Any audit not listed for your adapter refuses with exit 2 and says why. So does an audit missing a config section, or one run in an unconfigured git repo nested inside a configured one. It is not a pass and not a list of problems — read the message, which names what is missing.

Where reports go

Raw reports land inside .design-suite/ — tokens-findings.json, adapter-pattern-findings.json, layer-boundaries-findings.json, reduced-motion-findings.json and findings/. The scaffolded .design-suite/.gitignore keeps them out of git, because they quote your source. Delete them any time.

Upgrading from v0.1.0

  • Delete or git rm --cached the old reports: token_pipeline/findings.json, scripts/adapter_pattern_findings.json, scripts/layer_boundaries_findings.json.
  • Point any script or CI step at the new .design-suite/…-findings.json paths, or pass --out with the old path.
  • Add the three new file names to an older .design-suite/.gitignore.
  • Treat exit 2 as "could not check" — several refusals moved from 1 to 2.
  • Nested git repos now need their own setup, or the tools refuse.

What runs without you asking

The honest answer to the question most people have on install day.

The complete unattended surface

16 commands · 2 agents · 4 hooks

Nothing else in the suite starts itself. The 16 commands are read-only or ask before writing; the 2 agents are granted exactly Read, Grep, Glob — no Write, no Edit, no Bash, so none of them can change a file; the 4 hooks print a reminder after a tool call, or a note to Claude when a session opens, and nothing more — none of them writes a file.

How a command actually fires

Not the way the frontmatter suggests. Each command declares invocation: auto or explicit, but no runtime code reads that key — only the catalogue generator, preflight.py, doctor.py and the CI gates do. What Claude actually matches on is the description field, loaded at session start and compared against your phrasing.

So invocation: auto is a promise the description keeps, not a switch. Practically:

  • To make one fire: use the words in its description — or just type /name, which always works.
  • To stop one firing: disable the plugin, or name what you want instead. Nothing in .design-suite/ tunes triggering; it is description text only.

The rule behind the split

Blast radius, not difficulty. Read-only and report-only run automatically; anything that generates content or sets a project-wide convention waits for you.

One honest exception. /scaffold-screen is marked auto and it writes files. Either the rule has an exception nobody wrote down, or that frontmatter is wrong. It is listed here rather than quietly excluded.

Audits

9 audits, enumerated by the same discovery /repo-health and the MCP server use — so this cannot disagree with what actually runs. Each is reachable by its own command, by /repo-health, through MCP, or by running the script directly.

The zero that are switched off

A disabled audit stays listed on purpose. A check that quietly stopped running looks exactly like a check that ran and found nothing, so every surface has to name it.

AuditMeasured reason it is off
/audit-accessibility100% false positives — all 31 findings across two real projects were PDF-generating widgets judged against a screen text-size minimum. On one project it also had zero true-positive capacity.
/audit-copy73% of commit-gating findings wrong (19 of 26). The classifier calls everything “microcopy” as soon as a keyword matches, so body prose gets judged by label rules.
Neither is deleted, and neither is hidden. Silence from a disabled audit is not a pass — read it as a gap in coverage.

Hooks

Four, all advisory. A PostToolUse hook prints a reminder after a tool call; the SessionStart hook notices an unconfigured project and tells Claude to offer onboarding — it writes nothing, and a configured or declined project gets no message. None of them edits a file, blocks a tool call, or fails a build.

session_start_onboarding.pydesign-suiteSessionStart on startup | clearChecking whether this project is set up for design-suite...

Read this before you assume hooks are working. audit_on_edit.py only runs what your own .design-suite/hooks.map.json tells it to. That file used to ship as a TODO placeholder, so on-save nudges did nothing at all — and worse, the placeholder redirected the wrong flag, which would have made the hook fail silently even once wired. It now ships with a working default, and doctor.py reports an unconfigured map as a finding instead of saying nothing.

The only thing that can fail a commit

Nothing above blocks anything. Blocking is a separate, opt-in path: install_precommit_hook.py plus entries you explicitly mark preCommit: true. Nothing ships that way — you turn it on deliberately, for fast checks you are confident in.

Install recipes

Four situations people actually land in, if you would rather set up by hand than take the offer on session start. Five language adapters exist — see which stacks it can read.

A · You already have a design system

Tokens exist, docs exist, you want to know where the code disagrees.

  1. Install the plugin
  2. init.py to scaffold .design-suite/
  3. Fill the five required profile sections
  4. Map your docs to roles
  5. /audit-tokens, then /design-debt

B · You have no design docs at all

Code exists; nothing is written down.

  1. /survey — read the project first
  2. /map-project — confirm what it guessed
  3. /bootstrap-design-docs — one doc at a time, you accept each

Bootstrap is ⚠ use with review. It reverse-engineers what exists; it does not know what you intended.

C · Your stack has no adapter

Not Dart, TypeScript/web, Swift or Kotlin.

  1. The documentation skills still work
  2. Everything that scans source does not
  3. An unknown adapter is a hard error, never a quiet pass

That refusal is the point: a silent skip would look exactly like a clean codebase.

D · Five minutes, smallest possible

Just show me it works.

  1. Install
  2. init.py
  3. Fill source.root, source.fileGlob, adapters.lang
  4. /audit-tokens
Which plugins? design-suite is the base and goes anywhere. house-style is internal-only — client repos take the base plugin alone.

Your first five minutes

Run these in order. The second one matters most: it tells you which skills can actually run here before you try any of them.

# 1. Scaffold the config. Every value lands as a TODO — that is intended.
python3 "$CLAUDE_PLUGIN_ROOT/bin/init.py"

# 2. Which skills can run on THIS project, and what is blocking the rest?
python3 "$CLAUDE_PLUGIN_ROOT/bin/preflight.py" --json

# 3. Validate the profile. A fresh scaffold SHOULD report unresolved TODOs.
python3 "$CLAUDE_PLUGIN_ROOT/bin/doctor.py" --profile

# 4. What audits exist, and which are switched off?
python3 "$CLAUDE_PLUGIN_ROOT/bin/repo_health.py" --list

# 5. First real run.
/audit-tokens
Exit codes are load-bearing. 0 clean · 1 findings · 2 refused · 3 external · 4 declined · 5 stub. A refusal is never reported as a pass, because an audit that reports nothing must never be indistinguishable from a clean codebase.

Doc roles are a menu

There are 18 roles. You are not meant to have all of them. Map the ones you have, and decline the ones you genuinely do not — a declined role is recorded as declined, which is different from a role nobody got round to.

Anything --from-survey fills in is marked inferred: a machine's guess. Reviewing it is your job, and /ratify is how you sign off on one.

The MCP server

It ships, it registers itself on install, and it needs no configuration from you.

It exposes one tool per audit, with no required inputs. Disabled audits appear in that list too — listed and refusing, rather than vanishing. You would care if you want to drive these audits from another MCP client or script them outside Claude Code. Otherwise you can ignore it entirely.

Which version do you actually have?

Worth checking before you conclude a command is missing.

The plugin installs as a snapshot into a cache. If that snapshot is older than the repo, commands documented here simply will not exist for you — and nothing in Claude Code will tell you why. This was measured on a real machine: 30 commands installed against 50 shipped, because the cached copy was 226 commits behind.

# Compares what is installed against what the repo ships.
# 0 = in sync · 1 = drift · 2 = cannot determine (never reported as 0)
python3 "$CLAUDE_PLUGIN_ROOT/bin/installed_drift.py"

Removing it cleanly

Two things, not one. Uninstall the plugin — and, if you opted into commit gating, uninstall the pre-commit hook, which lives in your repo's git hooks and will otherwise keep running against a plugin that is gone. Your .design-suite/ directory is yours: deleting it is a separate decision.
