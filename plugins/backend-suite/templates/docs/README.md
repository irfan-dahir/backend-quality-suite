# Documentation templates

`/bootstrap-api-docs` installs these into a project that has no documentation layer. They are
the *shape* each document, not its content: a template says what belongs in an `API.md` and
why, and leaves the project to fill in what its API actually is.

**For the current inventory, read [`docs/CATALOG.md`](../../../../docs/CATALOG.md), not this
file.** It is generated by `bin/catalog.py` and names the exact template count, the role count, and
every role that has no template yet. No number is repeated here, deliberately: a count written in
this paragraph is a second copy that can disagree with the generated one, and this paragraph has
already been wrong once that way.

Every template is reachable through a role in `roles.json`, plus `PR.md.template` in
`house-style` because the PR process is org scope rather than universal. A role whose
document is emitted more than once — `components`, which produces an index plus one page per
component — declares a `pageTemplate` alongside its `template`, because a flat role-to-one-file map
cannot express it and the second template would otherwise read as an orphan.

**The count is not maintained by hand.** `roles.json` maps role to template, and `bin/catalog.py`
fails CI if a declared template is missing or if a template no role declares is present — an orphan
being a real finding, since `/bootstrap-api-docs` installs by role and cannot reach a template
nothing names.

That gate exists because this paragraph previously said "the four written are the ones the tooling
actually depends on" directly above an inventory listing seven. A hand-counted status line is the
same drift-prone claim as a hand-written catalogue, and gets the same treatment.

---

## What a template must do

Four rules, derived from what makes the originating project's docs actually work rather than from
taste:

1. **State its own role in the first paragraph.** A reader who opens the file cold must learn what
   it is for and who maintains it before anything else. Documents that fail this get treated as
   scratch space.
2. **Carry the reasoning, not just the rule.** `Buttons are 52dp` is forgettable and gets
   overridden; `Buttons are 52dp, enforced globally in the theme — do not override per-widget`
   survives. Every rule that could be mistaken for arbitrary needs its because.
3. **Mark what is unknown as unknown.** A template must never ship a plausible-looking default that
   a project then inherits without deciding. Use an explicit `<!-- DECIDE: ... -->` marker. An
   undecided question left visible is safe; one silently answered is not.
4. **Say who owns it and when it must change.** A document with no update trigger goes stale, and a
   stale doc is worse than a missing one because it is still trusted.

## Placeholders

| Marker | Meaning |
|---|---|
| `{{PROJECT_NAME}}` | Substituted at install time from the profile |
| `{{FRAMEWORK}}` | From `profile.json`'s `project.framework` |
| `<!-- DECIDE: question -->` | A real decision the project must make. `/bootstrap-api-docs` must surface every one of these and never resolve them itself |
| `<!-- DERIVED: how -->` | Content the bootstrap skill can reverse-engineer from the codebase and then ask the user to confirm |

## Inventory

Roles come from `.backend-suite/docs.manifest.json`. A role with no template means
`/bootstrap-api-docs` cannot scaffold it yet and must say so rather than skipping quietly.
This repo re-domained from a design suite to a backend/API suite; the design-era templates and
their roles left with the design domain, and the two kinds a role applies to are `library` and
`service` (see `roles.json`).

| Role | Template | Notes |
|---|---|---|
| `documentation-rules` | ✅ `DOCUMENTATION.md.template` | The governance doc. Written first because it defines how every other document is created, moved, and deleted — scaffolding the others without it produces files with no rules attached |
| `entry-point` (was `instructions`) | ✅ `INSTRUCTIONS.md.template` | The single entry point: mandatory rules, companion table, task router. Its invocation section deliberately does **not** restate per-skill tiers — it points at the plugin catalogue, because a hand-written copy cannot learn that a tier changed upstream |
| `decisions` | ✅ `DECISIONS.md.template` | Decision log. Almost entirely a format plus a discipline — `/sync-docs` writes entries, `/review-docs` checks them, release notes derive from them, so a hand-shaped entry breaks all three. Append-only, with a stated correction protocol |
| `api` | ✅ `API.md.template` | Records what exists: the public surface, endpoint by endpoint (a service) or method and model by method (a package). Marks each endpoint mockable or not, because a GET can be served from a fixture and a mutation cannot — faking a mutation's success produces a client that appears to work and discards data |
| `api-standard` | ✅ `API-STANDARD.md.template` | Records what is *required*: the response envelope, the error shape, versioning. Split from `api` so reviewing a proposed endpoint has a document to appeal to |
| `contributing` | ✅ `CONTRIBUTING.md.template` | Session-start and pre-PR checklists. `/review-docs` checks its examples against real code, so it is kept exact |
| `backlog` | ✅ `BACKLOG.md.template` | Cross-checked against real git branches by `/review-docs`, so branch names are kept exact |
| `brief` | ✅ `BRIEF.md.template` | Never written by a skill. When reality diverges from it, that goes in the decision log rather than being edited in |
| `builds` | ✅ `BUILDS.md.template` | Producing an artifact, as distinct from shipping one. Records whether CI is metered, since that changes whether adding a job is free |
| `deployment` | ✅ `DEPLOYMENT.md.template` | Service-only (`na` for a library). Includes the ownership boundary and a rollback section that must name what is *not* reversible |
| `production-readiness` | ✅ `PRODUCTION-READINESS.md.template` | The internal checklist for a deployed service. The client-facing summary is derived from it, never authored separately |
| `changelog` | ✅ `CHANGELOG.md.template` | Mostly a format contract plus the severity ↔ version mapping, with the cases that actually cause arguments called out. Load-bearing for a package whose consumers pin by tag |
| `deprecations` | ✅ `DEPRECATIONS.md.template` | The running ledger, deliberately separate from the release process that governs it |
| `common-mistakes` | ✅ `COMMON-MISTAKES.md.template` | Its whole value is the rule that every entry cites a real defect. That rule *is* the template |
| `rfc` | ✅ `RFC.md.template` | A proposal format, not a decision record — status moves Draft → Accepted/Rejected, and the outcome is linked into `decisions` rather than duplicated. Standalone, since no existing role fit a proposal-before-the-fact document |
| `release` | ✅ `RELEASE.md.template` | Never autonomous. Signing material is named, never pasted |
| `public-roadmap` | ✅ `PUBLIC-ROADMAP.md.template` | External-facing — deliberately distinct from the internal `decisions`/`backlog` roles, no internal reasoning or rejected alternatives |
| `postmortem` | ✅ `POSTMORTEM.md.template` | Written after, not during. Zero instances measured across the repositories the vocabulary was drawn from, so optional everywhere rather than expected anywhere |
| `pr` | ✅ `PR.md.template` (in `house-style`) | **Read at runtime** — `/draft-pr-description` copies the template, checklist and prefixes from it. The fenced `markdown` block is load-bearing: the skill looks for it. Org-scope, so it ships with the house-style plugin |

## Fragments

`fragments/` holds template content that is real template work but isn't a whole
document role on its own — it's meant to be pasted into whatever document a
project already has for that purpose. Not subject to the roles.json /
orphan-template gate above, since nothing installs it by role.

| Fragment | Paste into | Notes |
|---|---|---|
| `fragments/ROLLBACK-CONVENTION.md.template` | The `release` role, §5 ("What to do when a release is bad") | States the fixed convention — cut forward, never move a tag, attach a release note — and leaves what counts as a bad release, who has authority to cut the rollback, and where the incident gets recorded as `<!-- DECIDE -->`s each project answers for itself |
| `fragments/DEPRECATION-AND-BREAKING-CHANGES.md.template` | The `release` role, §6 ("Deprecating and breaking changes") | Combines the deprecation calendar and the breaking-change notice policy into one fragment rather than two near-identical small files, since they're a matched pair on the same lifecycle and audience |
| `fragments/SUNSET-PLAYBOOK.md.template` | The `deprecations` role, §4 | What it takes to remove a public surface from a shared layer without stranding a consumer: call-site closure, a grace period, and a removal record |

## Changing one

Take an existing document from a project whose docs work, strip the project-specific content, keep
the structure and the reasoning, and replace every decision with a `DECIDE` marker. That is how the
first templates were produced — they are generalisations of real files rather than inventions, which
is why they have opinions.

Adding a role means adding it to `roles.json` too, or CI fails. That is deliberate: a template
nothing declares is unreachable, because `/bootstrap-api-docs` installs by role.

**Watch for structure the tooling depends on.** A template that reorganises a document into
something more elegant can silently make it unreadable to the skills and audits that locate
sections by convention. Before changing a heading level or a section's position, check what
consumes it — the same discipline that used to apply to the design-era audit config applies to
every convention-bearing heading here.

Resist adding a template for a document no project has found useful. An unused template is a
maintenance cost that looks like coverage — the coverage claim above is only worth anything because
each of these corresponds to a role something actually reads.
