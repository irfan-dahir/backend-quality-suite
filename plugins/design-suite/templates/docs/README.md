# Documentation templates

`/bootstrap-design-docs` installs these into a project that has no documentation layer. They are
the *shape* of each document, not its content: a template says what belongs in a `DESIGN.md` and
why, and leaves the project to fill in what its design system actually is.

**For the current inventory, read [`docs/CATALOG.md`](../../../../docs/CATALOG.md), not this
file.** It is generated by `bin/catalog.py` and names the exact template count, the role count, and
every role that has no template yet. No number is repeated here, deliberately: a count written in
this paragraph is a second copy that can disagree with the generated one, and this paragraph has
already been wrong once that way.

Every template is reachable through a role in `roles.json`, plus `PR.md.template` in
`house-style` because the PR process is org scope rather than universal. A role whose
document is emitted more than once — `components`, which produces an index plus one page per
component — declares a `pageTemplate` alongside its `template`, because a flat role-to-one-file map
cannot express it and the second template would otherwise read as an orphan.

**The count is not maintained by hand.** `roles.json` maps role to template, and `bin/catalog.py`
fails CI if a declared template is missing or if a template no role declares is present — an orphan
being a real finding, since `/bootstrap-design-docs` installs by role and cannot reach a template
nothing names.

That gate exists because this paragraph previously said "the four written are the ones the tooling
actually depends on" directly above an inventory listing seven. A hand-counted status line is the
same drift-prone claim as a hand-written catalogue, and gets the same treatment.

---

## What a template must do

Four rules, derived from what makes the originating project's docs actually work rather than from
taste:

1. **State its own role in the first paragraph.** A reader who opens the file cold must learn what
   it is for and who maintains it before anything else. Documents that fail this get treated as
   scratch space.
2. **Carry the reasoning, not just the rule.** `Buttons are 52dp` is forgettable and gets
   overridden; `Buttons are 52dp, enforced globally in the theme — do not override per-widget`
   survives. Every rule that could be mistaken for arbitrary needs its because.
3. **Mark what is unknown as unknown.** A template must never ship a plausible-looking default that
   a project then inherits without deciding. Use an explicit `<!-- DECIDE: ... -->` marker. An
   undecided question left visible is safe; one silently answered is not.
4. **Say who owns it and when it must change.** A document with no update trigger goes stale, and a
   stale doc is worse than a missing one because it is still trusted.

## Placeholders

| Marker | Meaning |
|---|---|
| `{{PROJECT_NAME}}` | Substituted at install time from the profile |
| `{{FRAMEWORK}}` | From `profile.json`'s `project.framework` |
| `<!-- DECIDE: question -->` | A real decision the project must make. `/bootstrap-design-docs` must surface every one of these and never resolve them itself |
| `<!-- DERIVED: how -->` | Content the bootstrap skill can reverse-engineer from the codebase and then ask the user to confirm |

## The archetype extension set

Written against issue #95's archetype × role matrix, for the `design-system` extension set. All are
now declared in `roles.json` and reachable by `/bootstrap-design-docs`. The notes below are why each
template is shaped the way it is — the kind of thing that gets "simplified" back out otherwise.

| Template | Intended role | Notes |
|---|---|---|
| `COMPONENTS.md.template` | `components` | The index. **This role needs two templates** — an index and a page — because a single-file component role cannot express a corpus of per-component pages. Referenced as `{{doc:components}}` by `/promote-component` already |
| `COMPONENT-PAGE.md.template` | `components` | The per-component page. Its section names and order must stay identical to the schema template's required list, or every page written from it fails the check |
| `COMPONENT-SCHEMA.md.template` | `component-schema` | The machine-checkable shape of a component page. Split from `components` so the check has a document to appeal to |
| `ACCESSIBILITY.md.template` | `accessibility` | Built around the guaranteed / checked / **not checked** three-way split. A template listing only guarantees manufactures the false-clean the governing principle exists to prevent, so the third list is mandatory and an empty one is a finding |
| `TOKENS.md.template` | `tokens` | Opens with the "these tables document generated output, not the source" warning. Distinct from `profile.json`'s `tokens` field, which is a *code* pointer for the audit — the two are different artifacts and both are needed |
| `THEMING.md.template` | `theming` | Its coverage section requires the unwired-roles audit to be *run*, not estimated: a re-theming claim backed by a count of defined roles is the claim being wrong |
| `PATTERNS.md.template` | `patterns` | Composition recipes. Bars speculative patterns explicitly — a pattern that was never built reads as established practice and gets followed |
| `RESPONSIVE.md.template` | `responsive` | Space, not capability. Both consumer manifests already declare this as an `externalRole` |
| `CHANGELOG.md.template` | `changelog` | Mostly a format contract plus the severity ↔ version mapping, with the cases that actually cause arguments called out |
| `COMMON-MISTAKES.md.template` | `common-mistakes` | Its whole value is the rule that every entry cites a real defect. That rule *is* the template |
| `GALLERY.md.template` | `gallery` | Includes what a gallery is *not* evidence of, since it is routinely cited as proof of things it cannot show |
| `DEPRECATIONS.md.template` | `deprecations` | The running ledger, promoted out of `fragments/DEPRECATION-AND-BREAKING-CHANGES.md.template`. The *process* half stays in that fragment under `release`; the ledger and the policy are different documents with different readers |

Not written: `figma`. Issue #95 sizes it as small but gates it behind RFC-0002 §3f's four
preconditions, so shipping its template now would advertise a capability the suite has deliberately
deferred.

## Fragments

`fragments/` holds template content that is real template work but isn't a whole
document role on its own — it's meant to be pasted into whatever document a
project already has for that purpose. Not subject to the roles.json /
orphan-template gate above, since nothing installs it by role.

| Fragment | Paste into | Notes |
|---|---|---|
| `fragments/ROLLBACK-CONVENTION.md.template` | The `release` role, §5 ("What to do when a release is bad") | States the fixed convention — cut forward, never move a tag, attach a release note — and leaves what counts as a bad release, who has authority to cut the rollback, and where the incident gets recorded as `<!-- DECIDE -->`s each project answers for itself |
| `fragments/DEPRECATION-AND-BREAKING-CHANGES.md.template` | The `release` role, §6 ("Deprecating and breaking changes") | Combines the deprecation calendar and the breaking-change notice policy into one fragment rather than two near-identical small files, since they're a matched pair on the same lifecycle and audience |
| `fragments/SUNSET-PLAYBOOK.md.template` | The `deprecations` role, §4 — or the `promoting-components` role, §5, for a project that has no `deprecations` role | Promotion's inverse — what it takes to remove a component from the shared layer without stranding a consumer: call-site closure, a grace period, and a removal record |
| `fragments/ADAPTIVE-PATTERNS.md.template` | The `patterns` role, or the `responsive` role's capability section | Capability adaptation — input method, platform conventions, reduced motion, connectivity — kept deliberately separate from `responsive`'s space question, because conflating them is what produces layouts assuming a narrow window implies touch. A fragment rather than a role because it is the right *starting* size; a project whose version outgrows a page should give it its own document |
| `fragments/BRAND-ONBOARDING-INTERVIEW.md.template` | Used live by `/establish-brand-voice` Steps 1–2, then optionally pasted into the `brand-voice` role as an appendix or into `decisions` alongside that skill's own Step 4 entry | A reusable interview question set (tone spectrum, terminology, examples from the client's own materials, audience) for onboarding a new client's brand voice — distinct from `/establish-brand-voice` itself, which still owns drafting and sign-off. Not brand-sensitive on its own (issue #77) |

## Changing one

Take an existing document from a project whose docs work, strip the project-specific content, keep
the structure and the reasoning, and replace every decision with a `DECIDE` marker. That is how the
first templates were produced — they are generalisations of real files rather than inventions, which
is why they have opinions.

Adding a role means adding it to `roles.json` too, or CI fails. That is deliberate: a template
nothing declares is unreachable, because `/bootstrap-design-docs` installs by role.

**Watch for structure the tooling depends on.** `DESIGN.md.template` keeps the screen inventory at
the bottom of the file and uses `###` for each component, because the audit config locates both by
exactly those conventions. A template that reorganises a document into something more elegant can
silently make it unreadable to the audits that consume it — check `.design-suite/design-audit-config.json`
before changing a heading level or a section's position.

Resist adding a template for a document no project has found useful. An unused template is a
maintenance cost that looks like coverage — the coverage claim above is only worth anything because
each of these corresponds to a role something actually reads.
